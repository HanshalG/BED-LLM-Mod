# Bongard Confirmation64 Authorization Amendment

Date frozen: 2026-08-06

## Reason

The first confirmation freeze used the descriptive tier name
`full_policy_and_matched_mechanism`. The already frozen development claim
classifier actually emits `full_llm_native_development_signal` for that exact
conjunction. Leaving the names mismatched would make confirmation execution
impossible even after a full development pass.

No Bongard mechanics, development, or confirmation response existed when this
correction was made. No image, label, scientific endpoint, or model output was
opened.

## Exact Authorization

The legacy claim-report field `confirmation_execution_remains_unauthorized`
continues to mean that the development result alone cannot authorize an ad hoc
confirmation design. It does not override a confirmation protocol frozen before
development data.

The already-preregistered confirmation64 may execute if and only if all of the
following are true:

1. All four development blocks are mechanics-clean and independently replay.
2. The combined development result independently replays byte-for-byte.
3. The frozen claim report classifies the result as
   `full_llm_native_development_signal`.
4. The confirmation interface-v2 manifest and its independent verifier pass.
5. The exact block date, predecessor, model, balance, and account-wide daily
   budget gates pass before any request.

A policy-only tier, matched-mechanism-only tier, development null, missing or
tampered report, or stale confirmation manifest forbids execution. There is no
model substitution, task selection, threshold change, endpoint opening, or
partial-tier rescue.

## Scope

This amendment changes only the machine-readable tier name and the handoff from
the already frozen development classifier to the already frozen independent
confirmation. It does not change policies, prompts, likelihoods, controls,
tasks, seeds, dates, sample size, endpoint metrics, or confirmatory thresholds.
